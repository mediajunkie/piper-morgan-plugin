# Eval results: "a page is not the whole list" (piper-morgan-product #2005)

**Run**: 2026-10-14, Claude Code 2.1.296, `evals-2005/run.sh` (default agent model, Haiku judge with 3 votes and
PASS on ≥2). 5 suites × 2 variants × 3 cases × 3 runs = **90 runs, $7.47**, complete (`partial: false` on all
10 runs of the script). Generator: `evals-2005/build.py`. The connector is **mocked**: fixed sample data, and the
real tool description copied from the server code (MCP v14).

**Why**: on 2026-10-13, PM asked Claude Desktop (bare connector) "What are my open GitHub issues in Piper?" and
got "You have 30 open issues … that's the full set; the tool caps at 50". GitHub had 278. The server dropped
GitHub's `total_count`, and Lead fixed it (`total`, `truncated`, a full page of 50). The question here: how much
of the fix is server data, how much is wording, and how much is the plugin's skills?

## Setups

| Suite | `github_issues` payload | Tool description |
|---|---|---|
| prefix | 30 issues, `count: 30`, `capped_at: 50`, no total (the 10-13 shape) | as on the server |
| postfix | 50 issues, `count: 50`, `total: 278`, `truncated: true` (Lead's fix) | as on the server |
| postfix-desc | same as postfix | plus one sentence: "report total, say when the list is partial" |
| short | 4 issues, `total: 4`, `truncated: false` (control: the list really is complete) | as on the server |
| short-desc | same as short | plus the same sentence |

Variants: **bare** = `variants/bare-mcp`, the connector only. **full** = this plugin, the connector plus 3 skills.
Cases: "What are my open GitHub issues in Piper?" (list), "How many open GitHub issues do I have?" (count),
"Help me prioritize my open issues." (prioritize).

When the bare variant didn't call Piper, it tried `gh` and a subagent, found no shell, and told the user to run
`gh` themselves. The list and prioritize cases called Piper in every run, in both variants.

**Overturned judge FAILs (2 of 90):**
- full-postfix count, run 0 (votes PASS, FAIL, FAIL): "You have **278 open GitHub issues** … Piper only returned
  the first 50 of them." That's exactly the PASS condition.
- bare-postfix-desc prioritize, run 0 (FAIL ×3): "**I could only see 50 of your 278 open issues.** The other 228
  aren't ranked here." Same.

## What it says

1. **The data fix is what fixes it.** With the 10-13 payload, Claude called 30 "the full set" in every run that
   read it: 0 of 16, bare and full alike. With `total` and `truncated`, it reported 278 and said the list was
   partial in every run that read it (adjudicated: postfix 17 of 17, postfix-desc 16 of 16).
2. **Skills can't recover a missing number.** The full plugin scored 0 of 9 on the 10-13 payload, the same as
   bare, even though `prioritize-my-issues` already says "don't treat a partial list as the whole backlog". The
   payload never said it was partial.
3. **The extra description sentence adds nothing measurable.** The postfix runs were already at the ceiling
   without it. It caused no over-hedging on the short-list controls (18 of 18), so it's harmless, but not needed.
4. **What the plugin did add is routing.** For a GitHub question that doesn't name Piper, the full plugin sent it
   to Piper 15 of 15 times; the bare connector, 7 of 15. That's the plugin's measured value here: getting the
   question to Piper, not fixing the answer.
5. **No over-correction.** A complete short list was reported as complete in 33 of 33 runs that called Piper.

## Limits

- Claude Code's eval harness, not Claude Desktop or ChatGPT. Desktop has no `gh` fallback, so the bare routing
  gap may look different there. PM's live re-ask in Desktop is the real-user check (owed).
- Mocked data and a mocked tool listing (copied from code, not captured from the live server).
- A Haiku judge: 2 false FAILs in 90 runs, found by reading every FAIL outside the prefix suite among runs that called Piper (there were exactly 2). PASSes
  were spot-read, not all read.
- 3 runs per cell: enough to see 0-vs-all patterns, not to estimate small rates.
